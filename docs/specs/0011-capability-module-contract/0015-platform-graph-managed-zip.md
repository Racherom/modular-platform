# 0015. Platform graph and rendered managed zip

**Parent**: [0011. Capability and module contract](index.md)
**Extended by**: [0025](0025-slot-fields-config-delivery.md): how `api`, `planner` and `deployer-docker` read their `public`, `oidc` and `ingress` slots, how `ingress`'s `tls-mode`, `acme-email` and `web`'s `signed-out` reach their containers, `ingress` dropping its `web-upstream` value (`MP_WEB_UPSTREAM` stays a dev hook set only by the overlay), `http-ingress`'s `base_path` becoming optional, and `planner-mode: internal` set in the platform graph.
**Later replaced in part by**: [0016. Start the platform from one container](../0016-platform-one-container/index.md) (#32, after milestone 4): the platform `setup.sh`, the `authelia` step's questions and the deployer as a service of the platform's Compose file.

## Summary

The managed platform's eight modules become catalog entries and one graph file, `deploy/managed/graph.yaml`, and `libs/render`'s platform flavor turns that graph into the folder the release zip ships: the Compose file, config templates, `setup.sh` and README. The hand written Compose file, `db-init` and `setup.sh` go away; databases come from provision jobs, the public origin and ports from the ingress binding, the caller key from a binding field, and `postgres` serves TLS with a certificate from the issuer. This proves the contract can express the platform (0001 principle 2) and is what #23 builds on to replace a module.

- No binding cycle: backends use the ingress, the ingress uses only `cert-issuer`; `api` reaches the issuer URL through the ingress alias as today.
- `api` takes its first admin's email from its `oidc` binding's `admin_email` (one answer, asked by `authelia`, the module that owns the users); `api`'s config value `admin-email` goes away.
- `planner`'s and `deployer-docker`'s `platform-http-port` and `platform-https-port` come from their `ingress` binding, so a changed ingress port reaches the guard with no second answer.
- `api`'s caller key pair is an `api` setup step (`command: [caller-key, generate]`, a new subcommand of the `/api` entrypoint, since the image has no shell) writing `caller-signing-key` and `caller-public-key`; the signing key reaches `api` as its own secret (`MP_CALLER_SIGNING_KEY_FILE`, a bootstrap name), the public key travels as the `caller_key` field of its `planner` and `deploy-target` bindings (`{secret: caller-public-key}`, direction `to_provider`).

## Caller keys per consumer (sdk change)

- `planner` and `deploy-target` declare `env.caller_key: MP_CALLER_KEYS_DIR` on their provide; the SDK reads one PEM file per consumer from that folder at start (the same entry rules as the token clients directory, 0005).
- An `MP-Caller` token is checked only against the key of the consumer whose binding token matched (`CallerModule`), on top of 0005's checks; a token signed by another consumer's key is `invalid_token` (AC-18).
- `MP_CALLER_KEY_FILE` is removed from the bootstrap names and `sdk/CONTRACT.md`; a module with no `caller_key` directory accepts no caller token, as an unset `MP_CALLER_KEY_FILE` did.

## Platform render flavor

- `render.Platform(graph, catalog)` returns the folder: `docker-compose.yml`, `config/` (templates and env files), `setup.sh`, `.env.example`, `README.md`, `graph.yaml`. `task managed:render` writes it to `build/managed/` (not committed, like other build output). Image tags come from the catalog entries, whose `image` lines keep today's `# x-release-please-version` marker, so a release bumps the catalog and the next render follows; nothing rendered is under version control to drift.
- A golden test in `libs/render` renders the platform graph from the built in catalog with the platform's own images retagged to the fixed tag `0.0.0-test`, so release bumps never change the golden.
- It allows `publish`, `host_mounts` and setup steps, sets project `name: modular-platform`, and labels every service as 0013 says, with `deployment: platform`.
- `{install: <relative>}`, and the config default tokens `{uid}`, `{gid}`, `{install}`, render as `${MP_DIR}/<relative>`, `${MP_UID}`, `${MP_GID}`; `setup.sh` writes `MP_DIR` (its own folder, absolute) into `.env` once, like `MP_UID`.
- `setup.sh` is 0013's assembly. Its questions come in this order, which the render derives rather than lists (asked config values by their instance's place in the binding order, providers first, value names in order inside an instance; then each setup step's own questions): `ingress` domain (pattern: a DNS name with at least one dot, which Authelia requires), `ingress` origin (default `https://{domain}`; an empty answer takes it), `authelia` admin email, then `authelia`'s `users` step: admin user name, admin password. Piped stdin gives one answer per line in that order; `scripts/smoke-managed.sh` changes to feed an empty line for the origin (build task 19).
- `compose.dev.yaml` and `compose.ci.yaml` stay hand written overlays, applied as `-f build/managed/docker-compose.yml -f deploy/managed/compose.dev.yaml` (or `compose.ci.yaml`); they keep overriding `image:` and `build:` for the platform's own services, and the dev overlay sets `MP_WEB_UPSTREAM` in the ingress service's environment. Service and secret names they touch follow the rendered ones. The dev overlay no longer resets `ingress`'s `depends_on`, which is safe only while the rendered `ingress` depends on `cert-issuer` alone (it uses only the `trust` slot); a change to `ingress`'s bindings needs the overlay checked again. An overlay cannot change the image a setup step runs in, so dev and CI renders retag the platform's own images instead (`-image-tag`, see *Milestone 4 build findings*).
- The release zip (0009) packs `build/managed/`.
- Retired with milestone 4: `deploy/managed/compose.yaml`, `setup.sh`, `db-init/`, `Caddyfile`, `authelia/`, `cert-issuer/` (their content moves into the catalog modules' templates and setup steps). `deploy/managed/` keeps `graph.yaml`, the two overlays and a `README.md` pointing at the render.

## Milestone 4 build findings (2026-11-06)

What building tasks 17 to 19 settled that the text above left open. Each one is in the code and the golden files; the reasoning is short and inline.

- **Render command.** `task managed:render` runs `go run ./catalog/cmd/render-platform -graph deploy/managed/graph.yaml -out build/managed`. It loads the built in catalog, plans the graph as the planner does, and prints every problem. On a plan error it writes nothing and exits 1; otherwise it replaces `-out` as a whole. It lives in the `catalog` module because that module owns the embedded entries (`catalog.FS`), so `catalog` now imports `libs/planner` and `libs/render`.
- **Images in dev and CI (`-image-tag`).** `setup.sh` runs each setup step in its module's image (api's `caller-key` step in api's image), and an overlay changes only what `up` starts, never what `setup.sh` runs. So `-image-tag <tag>` retags every image under `ghcr.io/racherom/modular-platform/` at render time: `task dev:managed` renders with `dev` and builds the api image before `setup.sh`, `task smoke:managed` renders with `ci`. A release render passes no tag and takes every tag from the catalog. The overlays still set `build:` and the dev upstream. Runner up: a setup step image setting in the overlay, rejected because `setup.sh` reads no Compose file.
- **Question order is derived.** The platform flavor sorts asked values by their instance's place in the binding order (providers before consumers), value names in order inside an instance. That gives the list above with no list kept in code; 0013's *Install time* step 2 now says so. The static flavor keeps instance name order.
- **Delivery order.** Every flavor now delivers bindings by their consumer's place in the binding order, so a provider's own bindings are resolved before any binding to it. That is what lets a `{uses, field}` or `{uses, format}` source (`authelia`'s `ca` and `issuer`) and an SDK provider's `ca` from its bound `acme` slot find their value. Before this, both were `ErrNotRendered`.
- **`.env.example`, never `.env`.** The platform flavor writes its `.env` blocks to `.env.example`, and `setup.sh` writes `.env`. Unzipping a newer release over an install therefore never overwrites your answers. This closes AC-25's platform part, open since 0025 task 5.
- **The install folder.** `setup.sh` writes `MP_DIR` as the folder it sits in, single quoted, and stops when that path holds `'`, `\` or `$`, which a `.env` line cannot keep. It ends by printing `docker compose up -d --wait`.
- **Install tokens in the SDK.** An SDK config value whose default is `{uid}`, `{gid}` or `{install}/<relative>` gets no SDK default (`sdkgen`, `manifest.InstallToken`). The render fills its env; when that env is unset the value is `missing`, never the token text.
- **Caller keys problems.** An unreadable caller keys directory, or an entry that is not a regular file named by an instance or holds no Ed25519 PEM key, is `invalid_binding` at `provides.<capability>.caller_keys_dir`: one line per entry, naming the file, never its content (`sdk/CONTRACT.md`, CALL-6).
- **`deployer-docker`'s Linux capabilities.** The hand written service ran as root with Docker's default capability set (it had no `cap_drop`). The entry drops all and adds back three: `CHOWN` and `FOWNER` to give each deployed file to the platform user, `DAC_OVERRIDE` to read its secrets and write the deployments folder that user owns. That is stricter than before. It is allowed only because the platform flavor is not a deployed graph: 0022's rule (a deployed graph adds only `NET_BIND_SERVICE`) is unchanged, and the plan's `host_access` warning at `deployer-docker` names the three.
- **`postgres` plain until milestone 5.** The graph sets `postgres.tls: null`. A `tls-certificate` slot still renders as `ErrNotRendered` (the `tls-certificate` case of `tlsSlot` in `libs/render/bind.go`, which task 21 replaces), so `sslmode` is `disable` everywhere. Build task 21 binds `tls: cert-issuer.certs`.
- **The paper platform moved in.** The eight entries now live in `catalog/modules/`, and the capabilities `platform-api`, `tls-certificate` and `tls-certificate-provisioner` in `catalog/capabilities/`; the copies under `libs/contract/testdata/platform/` are gone, and the graph moved to `deploy/managed/graph.yaml`. The planner test and the render golden both plan that graph with the built in catalog. The golden retags the platform's own images to `0.0.0-test` instead of keeping a separate test catalog (the same effect as `-image-tag`, written again in `platform_test.go`, since `libs/render` cannot import `catalog`).
- **Release and smoke.** release-please bumps the image lines of the four platform entries (`api`, `planner`, `deployer-docker`, `web`); `deploy/managed/compose.yaml` left its list. The smoke job waits for the three database jobs (two provision jobs and the revoke job) instead of `db-init`. That count is written into `scripts/smoke-managed.sh` (`-eq 3`) and grows with each provisioner binding, so task 21's certificate job for `postgres` makes it four; and its secret scan skips files readable by group and others (`! -perm -0044`: public material a setup step writes with mode 0644, like `caller-public-key`) as well as `*.crt`.
- **`task dev:managed`** renders anew on each run and copies the render over `.dev/managed`, keeping `.env`, `secrets/`, `data/` and `deployments/`. When an install exists it runs `setup.sh` with no input, since there is nothing new to ask.

## Critical test scenarios

- `task managed:render` twice gives byte identical output; a golden diff test in `libs/render` over the platform graph, one golden per rendered template (**AC-16**, **AC-9**).
- The eight platform entries load from the built in catalog with no problem, and planning `deploy/managed/graph.yaml` gives `ok` (**AC-16**).
- `smoke-managed` on the rendered zip: install, sign in, deploy the sample stack, live state (**AC-16**).
- In that smoke run: `psql` from a test container to `postgres` without TLS is refused, `api` is ready with `sslmode=verify-full`, and the certificate's subject is `postgres.modular-platform.internal` (**AC-17**).
- An `MP-Caller` token minted with a second key that is not `api`'s, sent with `api`'s binding token: 401 `invalid_token` (**AC-18**).
- Planning the platform graph: `ok`, warnings `host_access` at `ingress` and `deployer-docker` only.

## Rationale (short)

Rendering the platform from a graph (your choice) is the only honest test that the contract expresses real modules: anything the hand written folder does that v1 cannot say shows up as a failing render, not as drift. Backends binding to the ingress follows how ingress controllers learn routes and is forced by the planner's cycle rule; the alternative (the ingress binding to each backend) needs the origin to reach `authelia` and `api` some other way, which means a second answer or a shared setting outside bindings. Moving the admin email to the identity provider's binding puts the answer where the users live, which #18 and #28 build on. Per consumer caller keys close a gap 0005 left (any key in the file could sign for any caller). Runners up: keep the hand written folder and only test the entries (no drift guard); let the ingress use backends with cycle exempt bindings (a new rule just for routing).
