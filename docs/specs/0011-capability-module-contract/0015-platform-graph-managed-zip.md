# 0015. Platform graph and rendered managed zip

**Parent**: [0011. Capability and module contract](index.md)

## Summary

The managed platform's eight modules become catalog entries and one graph file, `deploy/managed/graph.yaml`, and `libs/render`'s platform flavor turns that graph into the folder the release zip ships: the Compose file, config templates, `setup.sh` and README. The hand written Compose file, `db-init` and `setup.sh` go away; databases come from provision jobs, the public origin and ports from the ingress binding, the caller key from a binding field, and `postgres` serves TLS with a certificate from the issuer. This proves the contract can express the platform (0001 principle 2) and is what #23 builds on to replace a module.

- No binding cycle: backends use the ingress, the ingress uses only `cert-issuer`; `api` reaches the issuer URL through the ingress alias as today.
- `api` takes its first admin's email from its `oidc` binding's `admin_email` (one answer, asked by `authelia`, the module that owns the users); `api`'s config value `admin-email` goes away.
- `planner`'s and `deployer-docker`'s `platform-http-port` and `platform-https-port` come from their `ingress` binding, so a changed ingress port reaches the guard with no second answer.
- `api`'s caller key pair is an `api` setup step (`command: [caller-key, generate]`, a new subcommand of the `/api` entrypoint, since the image has no shell) writing `caller-signing-key` and `caller-public-key`; the signing key reaches `api` as its own secret (`MP_CALLER_SIGNING_KEY_FILE`, a bootstrap name), the public key travels as the `caller_key` field of its `planner` and `deploy-target` bindings (`{secret: caller-public-key}`, direction `to_provider`).

## Caller keys per consumer (sdk change)

- `planner` and `deploy-target` declare `env.caller_key: MP_CALLER_KEYS_DIR` on their provide; the SDK reads one PEM file per consumer from that folder at start (the same entry rules as the token clients directory, 0005).
- An `MP-Caller` token is checked only against the key of the consumer whose binding token matched (`CallerModule`), on top of 0005's checks; a token signed by another consumer's key is `invalid_token` (AC-18).
- `MP_CALLER_KEY_FILE` is removed from the bootstrap names and `sdk/CONTRACT.md`; a module with no `caller_key` directory accepts no caller token, as an unset `MP_CALLER_KEY_FILE` did.

## Platform render flavor

- `render.Platform(graph, catalog)` returns the folder: `docker-compose.yml`, `config/` (templates and env files), `setup.sh`, `.env.example`, `README.md`, `graph.yaml`. `task managed:render` writes it to `build/managed/` (not committed, like other build output). Image tags come from the catalog entries, whose `image` lines keep today's `# x-release-please-version` marker, so a release bumps the catalog and the next render follows; nothing rendered is under version control to drift.
- A golden test in `libs/render` renders the platform graph from a test catalog whose platform images carry the fixed tag `0.0.0-test`, so release bumps never change the golden.
- It allows `publish`, `host_mounts` and setup steps, sets project `name: modular-platform`, and labels every service as 0013 says, with `deployment: platform`.
- `{install: <relative>}`, and the config default tokens `{uid}`, `{gid}`, `{install}`, render as `${MP_DIR}/<relative>`, `${MP_UID}`, `${MP_GID}`; `setup.sh` writes `MP_DIR` (its own folder, absolute) into `.env` once, like `MP_UID`.
- `setup.sh` is 0013's assembly. Its questions, in this order: `ingress` domain (pattern: a DNS name with at least one dot, which Authelia requires), `ingress` origin (default `https://{domain}`; an empty answer takes it), `authelia` admin email, then `authelia`'s `users` step: admin user name, admin password. Piped stdin gives one answer per line in that order; `scripts/smoke-managed.sh` changes to feed an empty line for the origin (build task 19).
- `compose.dev.yaml` and `compose.ci.yaml` stay hand written overlays, applied as `-f build/managed/docker-compose.yml -f deploy/managed/compose.dev.yaml` (or `compose.ci.yaml`); they keep overriding `image:` and `build:` for the platform's own services, and the dev overlay sets `MP_WEB_UPSTREAM` in the ingress service's environment. Service and secret names they touch follow the rendered ones.
- The release zip (0009) packs `build/managed/`.
- Retired with milestone 4: `deploy/managed/compose.yaml`, `setup.sh`, `db-init/`, `Caddyfile`, `authelia/`, `cert-issuer/` (their content moves into the catalog modules' templates and setup steps). `deploy/managed/` keeps `graph.yaml`, the two overlays and a `README.md` pointing at the render.

## Critical test scenarios

- `task managed:render` twice gives byte identical output; a golden diff test in `libs/render` over the platform graph, one golden per rendered template (**AC-16**, **AC-9**).
- Milestone 1's paper platform: the eight entries load as catalog fixtures with no problem, and planning the platform graph gives `ok` (**AC-16**).
- `smoke-managed` on the rendered zip: install, sign in, deploy the sample stack, live state (**AC-16**).
- In that smoke run: `psql` from a test container to `postgres` without TLS is refused, `api` is ready with `sslmode=verify-full`, and the certificate's subject is `postgres.modular-platform.internal` (**AC-17**).
- An `MP-Caller` token minted with a second key that is not `api`'s, sent with `api`'s binding token: 401 `invalid_token` (**AC-18**).
- Planning the platform graph: `ok`, warnings `host_access` at `ingress` and `deployer-docker` only.

## Rationale (short)

Rendering the platform from a graph (your choice) is the only honest test that the contract expresses real modules: anything the hand written folder does that v1 cannot say shows up as a failing render, not as drift. Backends binding to the ingress follows how ingress controllers learn routes and is forced by the planner's cycle rule; the alternative (the ingress binding to each backend) needs the origin to reach `authelia` and `api` some other way, which means a second answer or a shared setting outside bindings. Moving the admin email to the identity provider's binding puts the answer where the users live, which #18 and #28 build on. Per consumer caller keys close a gap 0005 left (any key in the file could sign for any caller). Runners up: keep the hand written folder and only test the entries (no drift guard); let the ingress use backends with cycle exempt bindings (a new rule just for routing).
