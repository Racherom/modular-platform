## Summary
This is the slice 1 scaffold of spec 0001 and 0002: a stateless Go planner service (public and internal modes, rate limit, bearer auth), the pure `planner`, `render`, `contract` libs, the embedded catalog, a React Flow editor, the online tool compose and Caddy wiring, a smoke script and CI. The Go side is careful and matches the spec closely: client IP by hop count, strict decoding, deterministic output, secrets born on the host, no body logging. One real defect is in the editor (a stale problem list after reopening a same named file). The rest are robustness and hardening items. No security blockers found.

## Major
### 🟠 Reopening an edited graph file shows a stale problem list, `web/src/routes/index.tsx:63` and `web/src/components/GraphScreen.tsx:26`
**Problem**: `GraphScreen` copies its `plan` prop into `useState(plan)` once. The route remounts it only when `key` changes, and the key is `fileName|plan.graph.name`. Editing `graph.yaml` outside the tool (the normal workflow) and opening it again gives the same file name and the same graph name, so the component is not remounted. The canvas gets the new graph, but the problem list and the error markers keep the old plan's problems (`shownPlan.problems`).
**Why it matters**: A user fixes a file, reopens it, and still sees the old errors (or sees no errors for a newly broken file). That undermines the planner as the one validator, and the tests do not cover it.
**Suggested fix**: Do not mirror a prop into state. Hold only the "newer plan from a 422 render" as state and prefer it only while it belongs to the current prop (reset it when `plan` changes), or key the screen on something that changes per open (an open counter or the plan object identity). Add a test that opens two different files with the same names.

## Minor
### 🟡 Prototype keys break the layout, `web/src/graph/layout.ts:16` and `:23`
**Problem**: `provider in consumers` and `column[name]` use plain objects. A provider value such as `constructor` or `__proto__` (the planner returns invalid graphs to the editor along with their problems) makes `consumers[provider]?.push` call a non function and throw; an instance literally named `constructor` makes `column[name]` return a function and the positions become NaN.
**Why it matters**: A crafted or mistaken file blanks the screen instead of listing `unknown_provider`.
**Suggested fix**: Use `Map`/`Set`, or `Object.hasOwn`, for these lookups.

### 🟡 Timeout answer is off contract and the work is not cancelled, `services/planner/internal/api/server.go:86`
**Problem**: `http.TimeoutHandler` answers 503 with a hand written body and no `Content-Type`, and 503 is not in `contracts/openapi/planner.yaml`. Planning and rendering ignore the context, so the goroutine keeps running after the 10 second deadline.
**Why it matters**: Clients cannot rely on the documented shapes; a slow input keeps burning CPU after the client got its error (inputs are capped at 1 MB, so this is bounded).
**Suggested fix**: Document 503 in the contract with the `ProblemList` shape and set the content type; check `ctx.Err()` between phases in `Render`.

### 🟡 Rate limiter memory is bounded only by time, `libs/platform/ratelimit.go:47`
**Problem**: One bucket per client key is created on first sight and dropped after 10 idle minutes, with no cap. An attacker with many IPv6 /64 networks (or many IPv4 addresses) grows the map as fast as requests arrive; the limiter itself never refuses to create a bucket.
**Why it matters**: The public planner promises to be safe on the internet; the map is the one unbounded structure.
**Suggested fix**: Cap the number of buckets (fall back to a shared bucket or reject when full), or add a coarse global limiter in front.

### 🟡 Secret Compose name collision is a 500, not a plan problem, `libs/render/render.go:94`
**Problem**: `<instance>-<name>` can collide (instance `a-b` with secret `c`, instance `a` with secret `b-c`). The renderer returns a plain error, which the service turns into a 500 "The planner failed". It cannot happen with today's catalog (one secret, `password`) but will with the next module.
**Why it matters**: A valid looking graph fails with an internal error that the user cannot fix.
**Suggested fix**: Detect it in `libs/planner` as a plan error with a path, or make the Compose name collision free (a separator that names cannot contain is not possible in a Compose secret name, so check up front).

### 🟡 `libs/go.mod` marks every dependency `// indirect`, `libs/go.mod:9`
**Problem**: `compose-go`, `distribution/reference`, `sigs.k8s.io/yaml` and `golang.org/x/time` are imported directly by `libs` but listed as indirect.
**Why it matters**: `go mod tidy` would rewrite the file, so CI's codegen diff check or a later tidy produces noise; it also hides what the module really depends on.
**Suggested fix**: Run `go mod tidy` in `libs/`, `catalog/`, `services/planner/` and commit the result.

### 🟡 Stray root `package.json` and `package-lock.json`, `package.json:2`
**Problem**: The root file depends on `nodejs@^0.0.0` (an unrelated npm package, not the Node runtime) and `pnpm`. Nothing in the Taskfile, CI or Dockerfiles uses it (the web image installs pnpm itself).
**Why it matters**: An unused, unreviewed dependency tree in a project that handles secrets is supply chain surface for no benefit.
**Suggested fix**: Delete both files, or document and pin what they are for.

### 🟡 No security headers or container hardening on the public ingress, `deploy/online/Caddyfile:19` and `deploy/online/compose.yaml:7`
**Problem**: The ingress and web Caddy send no CSP, `X-Content-Type-Options`, `Referrer-Policy` or HSTS (in `acme` mode). Containers run without `cap_drop: [ALL]` and `no-new-privileges`; `ingress` is not `read_only`.
**Why it matters**: The tool is meant to run on a public host; the bundle only loads its own scripts, so a strict CSP is cheap and the compose hardening costs nothing.
**Suggested fix**: Add a header block (CSP limited to self, nosniff, referrer policy, HSTS when `acme`) and the compose hardening options.

### 🟡 The production TLS path is never exercised, `deploy/online/Caddyfile:12`
**Problem**: `(tls-acme) {}` is an empty snippet and the smoke job only runs `PLATFORM_TLS=internal`. I could not verify that Caddy accepts an empty snippet and `import tls-{$PLATFORM_TLS}` with `acme`, and the default in `compose.yaml` is `acme`.
**Why it matters**: If it does not parse, the documented production setup fails at first start and CI stays green.
**Suggested fix**: Add a `caddy validate` run with `PLATFORM_TLS=acme` to the smoke script or CI; if the empty snippet is rejected, put a harmless directive in it.

### 🟡 Dev server binds all interfaces with repo wide file access, `web/vite.config.ts:45`
**Problem**: Under `MP_DEV_PROXY=1` Vite listens on `0.0.0.0` with `fs.allow` set to the repo root. Only the `Host` header is restricted (`allowedHosts`).
**Why it matters**: Anyone on the same network can request `/@fs/...` files inside the checkout (including `deploy/online/.env`) by sending the allowed Host header.
**Suggested fix**: Bind to the docker bridge/host-gateway address only, or narrow `fs.allow` to `web/` and `samples/`.

### 🟡 The AC-3 "no secret" check is weak, `scripts/smoke.sh:38`
**Problem**: It greps for the literal `POSTGRES_PASSWORD=`. A leaked generated value (random hex) or any other variable name would pass.
**Why it matters**: AC-3 and principle 6 (no secret value in a zip) are the platform's core safety claim and the CI gate for them is nearly vacuous.
**Suggested fix**: Assert the zip's file list is exactly the five expected files and that nothing under `secrets/` exists; optionally grep for 64 hex character runs.

### 🟡 Release plumbing gaps, `deploy/online/versions.env:4` and `.github/workflows/release.yml:21`
**Problem**: `MP_VERSION=0.0.0` names images that do not exist until the first release, so `task online:up` cannot pull them before then. release-please pull requests opened with the default `GITHUB_TOKEN` do not trigger the `pull_request` CI workflow, so the release PR may merge unchecked.
**Why it matters**: A first-run failure for anyone following the README, and an unchecked release path.
**Suggested fix**: Document building with `task images` plus `MP_VERSION=dev` for local runs; give release-please a PAT or app token (or run CI on the release branch push).

- ⚪ `libs/render/templates/setup.sh.tmpl:6`, secret files are 0600 and owned by the host user; bind mounted secrets keep that, so a future module image running as another non root uid cannot read them. Fine for `postgres` (its entrypoint reads as root first); worth a note in the module authoring docs.

## Strengths
- Principle 11 is implemented exactly (hop count from the right, unmapped IPv4, IPv6 /64 key) and the test proves a forged leftmost `X-Forwarded-For` cannot dodge the limit; bodies, queries and client addresses never reach the access log, and a test checks it.
- The planner is pure and deterministic (sorted problems and bindings, Tarjan cycle detection with a stable reported cycle), and the zip is byte reproducible (fixed timestamps, sorted entries).
- Strict decoding is done in one place (`DecodeGraph`) and reused by the middleware, catalog loader and tests; the Go and TypeScript writers are tied together by the same fixture files.
- `setup.sh` is careful: never overwrites, verifies the random read, noclobber against races, umask 077.
- CI actions are pinned by commit SHA, permissions are least privilege, and generated code is diff checked.
